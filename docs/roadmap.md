# 开发计划

本路线图按依赖推进，不以尚未确认的人力和每天投入时间承诺日期。所有未完成框均代表待实现事项；文档完成不等于游戏功能完成。

## 总览

| 阶段 | 主要产物 | 进入下一阶段的门槛 |
| --- | --- | --- |
| M0：规格与环境 | 设计基线、锁定版本和可导出的空工程 | 开发者能打开工程，Android 空包能安装 |
| M1：操作训练场 | 一只鸡、移动、射击、技能、木桩 | 真机能同时移动和攻击，遮挡与命中清晰 |
| M2：完整人机原型 | 菜单、机器人、地图互动、胜负和重开 | 连续完成并重开 10 局，无阻断问题 |
| M3：联网技术验证 | 同一套战斗逻辑、独立服务端、两个客户端 | 服务器统一判定，两端状态和结果一致 |
| M4：内容验证版本 | 鸡／猪／马、小农场与泥地 | 三种定位可感知，场景互动有用 |
| M5：小规模在线 Alpha | 房间、接入验证、必要平台能力、反馈 | 实际外网能进房完成对局，失败可恢复 |
| M6：TapTap 测试与发布准备 | 审核资料、签名包、商店物料 | 满足所选测试／上线形式的要求并通过审核 |

默认依赖为 M0 → M1 → M2 → M3 → M4 → M5 → M6。平台准备在 M0 开始摸底；M2 后就做联网技术验证，避免等动物全部完成才发现架构问题。M6 的平台获准时间不由开发里程碑保证。

## M0：规格与环境

- [ ] 在 [决策记录](decisions.md) 确认 Android 横屏优先、原型人机模式、每只动物一个主动技能的默认方案。
- [ ] 选定并记录一个稳定 Godot 4.x 完整版本；安装完全匹配的导出模板。
- [ ] 建立 `game/project.godot`，先选 Compatibility 渲染器；配置窗口、横屏、输入动作和基础碰撞层。
- [ ] 配置 Android 导出环境，构建并安装一个空场景 APK；记录一台实际目标手机及系统版本。
- [ ] 增加 Godot 缓存、构建目录和签名凭据的忽略规则；确认 `.uid` 等应提交的源侧文件按所选 Godot 版本保留。
- [ ] 明确像素风或手绘卡通等美术方向，先准备占位图和一个遮挡样例。
- [ ] 开始了解 TapTap 开发者身份、计划测试形式与所需接入；建立平台待办，避免临近测试才发现缺项。

验收：新环境能按 README 打开工程；空 APK 在目标手机启动；仓库没有生成缓存或密钥。当前会话未在 PATH 中找到 `godot` 命令，这只代表未发现命令行入口，不代表本机一定没有安装编辑器。

## M1：操作与战斗训练场

- [ ] 按 [首个原型任务书](first-prototype.md) 完成 P01–P07。
- [ ] 左摇杆／键盘移动，脚底碰撞，前后 Y 排序，受控 Camera2D。
- [ ] 独立瞄准、普攻间隔、弹体、受击、血条、命中反馈。
- [ ] 鸡的主动增速技能、冷却、范围内辅助选敌。
- [ ] 原型打包到手机，多指同时操作和切后台恢复检查。

验收：沿围栏前后绕行时遮挡正确；可边移动边射击；木桩只受一次有效弹体伤害；技能冷却不会因连点绕过。记录操作视频和最明显的三个手感问题。

## M2：一局完整的人机游戏

- [ ] 完成 P08–P12：机器人、干草堆、玉米、对局控制、菜单、结算与重开。
- [ ] 采用 120 秒／先 5 分结束、3 秒复活和 1 秒保护的默认规则，参数可配置。
- [ ] 将输入命令、战斗判定和画面反馈分开，为下一阶段复用。
- [ ] 邀请 3–5 位玩家试玩，记录理解困难、操作误触、瞄准失误和地图问题。
- [ ] 修复会阻止一局完成的问题，补充真实截图与 APK 构建说明。

验收：连续 10 局从开始到结算并重开；血量、冷却、计分、破坏物与道具每局正确重置；至少一台实际 Android 手机完成相同流程。此时达到第一个可交付的可玩原型。

## M3：尽早验证联网架构

- [ ] 使用同项目的 Godot 无界面服务端，连接两个独立客户端；先本机，再同一局域网。
- [ ] 明确实体 ID、玩家归属、命令序号、服务器 tick 与协议版本。
- [ ] 输入发送到服务端；移动、技能、伤害、道具、重生与胜负统一由服务端决定。
- [ ] 远端角色插值；验证本地移动预测与服务器校正是否需要，记录成本与误差。
- [ ] 加入基础的命令合法性、频率、归属和重复请求检查。
- [ ] 检查迟到快照不覆盖新状态、掉线能退出、结束事件不重复。
- [ ] 在模拟 RTT 100ms、少量丢包的条件下记录体验，决定后续同步优化优先级。

验收：两端打一整局，最终分数与胜负一致；客户端不能直接指定伤害、血量或冷却结束；服务器可无 UI 运行。手机局域网直连成功不代表外网房间已完成。

## M4：三只动物与农场特点

- [ ] 用配置与独立能力行为增加猪、马，复用角色生命、移动和状态组件。
- [ ] 增加近战扇形、泥浆区域、碰墙停止的冲锋，复用统一命中流程。
- [ ] 完成三动物选择界面、角色识别和农场第一版统一美术／音效。
- [ ] 增加天然泥地；检查多种减速来源、离开区域、死亡和重生后的清理。
- [ ] 验证最多 4 人混战的玩法需求与性能，再确定正式人数和是否组队。
- [ ] 复核所有新能力的联网结果及地图边界情况。

验收：试玩者可以描述三种动物的不同策略与弱点；近战、远程、冲锋、区域技能都能被看清和反制；没有因新动物复制出第二套基础战斗逻辑。

## M5：小规模在线 Alpha

- [ ] 在可访问的服务器部署战斗进程，明确 UDP 端口、防火墙与进程生命周期。
- [ ] 实现创建／加入房间、准备、加载同步、开局、离开和连接失败提示。
- [ ] 明确掉线策略：初期采用离局并结算为退出；若要断线重连，另做会话恢复和完整状态快照。
- [ ] 增加房间准入验证、玩家身份与角色归属绑定；若接入平台登录，由后端验证票据。
- [ ] 完成 TapTap 必需平台能力的 Android 技术验证与对应真机检查。
- [ ] 在实际外网、多种手机与移动网络上测试，记录延迟、崩溃、帧时间和一局完成率。
- [ ] 检查服务器资源与费用；公开测试规模按测得的单房间成本决定。

验收：不同网络中的玩家能进同一房间并完成对局；连接失败与服务端关闭有可恢复提示；异常数据不会直接改变其他玩家血量；达到预先选定设备的性能目标。

## M6：TapTap 测试与发布准备

- [ ] 按 [发布准备](taptap-release.md) 核对游戏形式、资料、资质与平台接入。
- [ ] 固定应用包名、签名与版本号，保管签名备份；验证覆盖安装。
- [ ] 检查素材授权、隐私说明、权限行为以及审核所需的实际流程。
- [ ] 准备图标、截图、实机视频、简介、反馈入口与已知问题。
- [ ] 完成选定范围的测试审核，按反馈修复；满足条件后再安排正式上线。
- [ ] 给真实发布版本打标签，保留版本说明和回退包。

## 每次开发的工作方式

先从某一里程碑取一个小任务，写清完成标准，再实现并在 Godot 或真机验收。提交时记录完成内容、验证环境、已知问题和下一步。每次只推进少量任务，避免同时增加新动物、联网和商业系统。

阶段时长需结合现有 Godot 经验、每天投入、素材来源和服务器预算再估计。最先安排的实际工作是 M0 的空工程与 Android 导出，以及 M1 的“移动＋遮挡”样例。
